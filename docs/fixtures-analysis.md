# Разбор живого захвата acme — fixtures/live-acme (2026-10-01)

Источник: реальный plan9port-acme, запущенный через MITM-обёртку
`scripts/devdraw-tee.sh` (режим capture-pipe, legacy: клиент сам форкает
devdraw, MITM стоит ровно на его pipe). Файлы: `c2s.bin` (1933 B),
`s2c.bin` (482 B), `capture.log` (68 строк — лог того же захвата).
Прогон fixture-тестов: `cargo test -p p9draw-protocol --test live_capture`.

## 1. Итог сверки

| Метрика | Значение |
|---|---|
| Кадров c2s / s2c | **35 / 33** (байты декодированы целиком, 1933/482 B, без обрывков) |
| Сверка с capture.log | 68/68 строк: тип, тег, размер каждого кадра совпали |
| Rerror | 0 в обе стороны |
| Ответы на RPC | 30 Twrdraw ↔ 30 Rwrdraw (counts 1:1, FIFO), 2 Trddraw ↔ 2 Rrddraw |
| Длительность сессии | ~45 мс (Tinit @…570 → последний кадр @…615, метки ms) |

Порядок в `capture.log` **не** строго хронологический: при равных мс
строки c2s/s2c идут в порядке сброса буферов двух направлений (пример:
ответ `Rwrdraw count=45` залогирован раньше строки запроса `Twrdraw 64
0a`). Для порядка сообщений авторитетны .bin.

## 2. Хронология (по байтам)

1. **Handshake** — `Tinit` (18 B): `00 00 00 12 01 0e | 00 00 00 00 |
   00 00 00 04 61 63 6d 65` → winsize="" label="acme" → `Rinit` (6 B).
   `Tctxt` в потоке нет — legacy-режим (SPEC §2.1): acme сам `$wsysid`
   не ставит (см. OPEN-1).
2. **draw-init**: `Twrdraw "JI"` (`4a 49`: image0:=screen + read info) →
   `Trddraw 145` → `Rrddraw 144` = 12 полей `%11d `: clientid=1,
   infoid=0, chan=**x8r8g8b8**, rect 1939×1293 → `Twrdraw "q\x01d"`
   (`71 01 64`: query dpi) → `Rrddraw 12` = **192 dpi**.
3. **Тайлы и окно**: `b` id1 GREY1 (chan `31 00 00 00`, value
   `ff ff ff ff`, repl=1), `b` id2 GREY1 (value `00 00 00 ff`),
   `A` allocscreen (id=1, imageid=0, fillid=1, public=0), `b` id3 —
   **окно**: screenid=1, chan `28 18 08 68` = 0x68081828, R=clipR=
   1939×1293; далее цветные 1×1 repl-тайлы (0xAAFFFF, 0xFFFFFF,
   0x9EEEEF, 0x8888CC, 0xFFFFAA, …) и 17×16-маски.
4. **Отрисовка**: шесть `d`-команд (composite), одна в паре с `v`
   (flush) внутри одного Twrdraw — count=46 = 45+1; две пачки по 225 B,
   пять `f` (free) — id освобождаются сразу.
5. **Финал (три последних кадра c2s)**:
   `Twrdraw b id=0x12` → `Trdkbd4` `00 00 00 06 01 20` (tag=1) →
   `Trdmouse` `00 00 00 06 02 02` (tag=2). Ответов на эти два — нет
   (ждут событий пользователя). Затем EOF в обе стороны, без Rerror.

## 4. Статусы OPEN-вопросов (детали — SPEC.md §8)

1. `$wsysid` — **STILL-OPEN**: capture в legacy-режиме (нет `Tctxt`);
   генерация name/id не наблюдаема. Нужен захват серверного режима.
2. chan macOS — **STILL-OPEN**: capture на Linux/X11 (x8r8g8b8, 192 dpi);
   `mac-screen.c` не сверялся.
3. Порядок байтов пикселя / упаковка value — **CONFIRMED** (провод: §3;
   память: libmemdraw `memsetchan`/`_rgbatoimg`/`_memfillcolor` —
   пиксель x8r8g8b8 в памяти `[B,G,R,X]`, `value` = канонический RGBA
   (D-цвета: `DPaleyellow` = `0xFFFFAAFF`), конвертируется `_rgbatoimg`;
   детали — SPEC.md §8 п.3, реализация `Chan::rgbatoimg`).
4. Лимит кадра на сервере — **STILL-OPEN**: максимальный кадр в capture
   235 B, лимит не нагружался.
5. `msec` мыши — **CONFIRMED** (interactive-захват, §6): база = ms с
   загрузки ОС (uptime); биты 16..23 на проводе замещены `resized`.
6. bit30 у `'e'`/`'E'` — **STILL-OPEN**: эллипсов в capture нет.
7. Мультиклиентная маршрутизация — **STILL-OPEN**: один legacy-клиент.

## 5. Почему capture-инстанс acme завершился после init

Протокол-видимая картина: init завершён **полностью и без ошибок** — все
32 draw-RPC получили ответы, `Rinit` пришёл, ноль `Rerror`, кадры без
обрывков. Последние три кадра c2s — обычный вход в цикл событий acme:
после отрисовки стартового окна клиент поставил асинхронные чтения
`Trdkbd4` (tag=1) и `Trdmouse` (tag=2) и блокируется в ожидании
пользовательского ввода. За 45 мс сессии ввод появиться не мог.

**Гипотеза (основная):** внешнее завершение сессии при заблокированном
клиенте — процесс-группу acme убили (или закрыли управляющий терминал),
pipe закрылся, реальный devdraw получил EOF и вышел; MITM увидел чистый
EOF в обе стороны. Ничего в протоколе к смерти не привело.

**Гипотеза (альтернативная):** acme завершился сам по ошибке, невидимой
для MITM (stderr-сторона: свой 9P-сервис `/mnt/acme`, шрифты, окружение)
— на drawfcall-проводе такого следа не бывает.

**Что проверить:**
- в capture-pipe логировать, *какая* сторона первой увидела EOF, и
  `waitpid`-статус `devdraw.real` (кто умер первым — клиент или сервер);
- перезапустить acme с перехватом stderr в файл — сообщения acme
  ("can't post…", шрифты) идут туда, не в протокол;
- `strace -f -e trace=read,write,exit_group` — порядок выходов процессов;
- контрольный прогон **без** MITM в том же окружении: если acme так же
  умирает после init — причина средовая, не p9draw;
- удержать сессию живой синтетическим событием мыши → появятся первые
  `Rrdmouse` (закроют и OPEN-5: единицы `msec`).

## 6. Interactive-захват — человек за acme (fixtures/live-acme-interactive)

2026-10-01, тот же MITM (wrapper capture-pipe), но acme вёл **живой
человек**: мышь и клавиатура ~минуту. Сессия осталась жива на момент
снятия — последний кадр в .bin может быть обрезан (тесты декодируют до
первого оборванного хвоста, сверка с capture.log с допуском ±1).

### Итог сверки

| метрика | значение |
|---|---|
| c2s | 74 810 B, 1128 кадров, обрезков нет |
| s2c | 17 240 B, 1126 кадров, обрезков нет |
| Twrdraw / Rwrdraw | 631 / 631 (64 452 B draw-команд) |
| Trdmouse / Rrdmouse | 457 / 456 (запрос без ответа — сессия жива) |
| Trdkbd4 / Rrdkbd4 | 12 / 11 (набрано «Hello GLM!» + спец-rune) |
| Tmoveto / Rmoveto | 15 / 15 |
| Tcursor2 / Rcursor2 | 10 / 10 (в init-захвате не появились) |
| Trddraw / Rrddraw | 2 / 2 (ASCII-инфо) |
| Rerror | 0 |

### Rrdmouse: `resized` — НЕ 17-й байт payload (баг декодера исправлен)

Кадр 23 B = size[4] + tag[1] + type[1] + 17 B. drawfcall.c:
`PUT(p+6,x) PUT(p+10,y) PUT(p+14,buttons) PUT(p+18,msec); p[19] = resized`.

- `resized` пишется **поверх байта 1 группы msec** (offset кадра 19):
  во всех 456 кадрах frame[19] = 0 (ресайзов не было); биты 16..23 msec
  по проводу не передаются;
- байт 22 кадра **не пишется ничем** (sizeW2M его считает, convW2M не
  пишет): во всех 456 кадрах там стабильный `0x20` — мусор
  переиспользуемого буфера (пробелы из предыдущего Rrddraw); его не
  читает никто;
- старый декодер брал `resized` с байта 22 → в capture.log печатался
  мусор `resized=32`. Исправлено: decode — `(msec>>16) & 0xFF`, encode —
  флаг в байт 1 msec + пад-байт 0 (crates/protocol, golden-тесты
  обновлены, byte 22 исключён из побайтового сравнения).

### OPEN-5 (msec) — CONFIRMED

msec = ms с загрузки ОС (uptime): первое значение 1 342 223 032 мс ≈
15.53 сут; /proc/uptime hlab на момент снятия ≈ 15.63 сут (≈2.4 ч
спустя). Дельты соседних событий 1–20 мс (медиана 18, паузы до 963);
единственная аномалия −65522 — 64K-граница (0x5000fffe → 0x5000000c),
след перекрытия msec/resized. Для acme значимы только дельты.

### Клавиатура

Только Trdkbd4/Rrdkbd4 (legacy Trdkbd/Rrdkbd не появились). Rune — u32 BE:
`U+F014` (PUA plan9port, KF=0xF000 — спец-клавиша; какой X-keysym за ней
стоит, не вскрывалось) и `Hello GLM!`. 12 запросов → 11 ответов: один
запрос остался в очереди живой сессии.

### parse_drawcmds на реальном потоке

Все 631 Twrdraw (64 452 B) разобраны `parse_drawcmds` **без единой
ошибки** — неизвестных опов нет (перечислять нечего). Первые опы кадров:
v 461, d 48, b 46, l 62, f 6, i 4, A/J/q/Y — по 1; внутри кадров также
`I`. Тест: crates/protocol/tests/interactive_capture.rs.
